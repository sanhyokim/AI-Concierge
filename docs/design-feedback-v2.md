# 設計レビューv2への返答

確認日：2026年10月4日

前回の主要な指摘は概ね反映されています。v2を設計の基礎として進めることに賛成します。全面的な再レビューは不要です。以下の3点を統合時に修正し、回線の契約情報を確認した後、検証計画と実装用プロンプトを具体化してください。

## 1. 部分減速は「専用設定の制約」と「実現可否」を区別

要約の「どちらにも番号の部分だけ遅くする設定はない」が、部分減速そのものが実現できないという意味に読めます。本文3-1にあるOpenAIの指示文による方法は、検証候補として維持してください。

OpenAI公式リファレンスでは、speedは応答中に変更できず、生成後の音声に対する調整である一方、指示で話し方を速く・遅くすることも可能と説明されています。ただし、日本語の番号・日時だけ確実に減速できることを保証する資料ではありません。

改訂する表現：

> OpenAIのspeed設定は応答間でのみ変更可能。重要部分だけの減速は、指示文、または同じ声で応答を分ける方法を検証する。ConversationRelay＋ElevenLabsの日本語SSMLでは部分減速を前提にしない。案BのGoogle／Polly音声を含め、実際の電話で自然な「通常→減速→通常」が成立した方法を採用する。

Pollyの候補は、音声ID・エンジン・ConversationRelayの対応・SSMLの対応を一組として確認してください。Polly本体で使えることだけでRelay経由も利用可能とは扱いません。

## 2. スマホのWeb画面からの切替を、完成条件として維持

文案R1の「常時転送が成立しなければキャリア側で切り替え、設定待ちを表示する」は、元の「出先からWeb管理画面で簡単に普通受電／AI受電を切り替える」要件を満たすとは限りません。

改訂する表現：

> PC・スマートフォンのWeb管理画面から、普通受電／AI受電／時間指定を設定でき、設定の保存後、次の着信から意図した動作になることを完成条件とする。キャリア側の手動操作を必要とする案は代替運用として提示し、同等の要件達成と扱わない。対応できる経路が成立しない場合は、その不足と代案を示し、要件を変更する判断をユーザーに求める。

契約情報を受け取る前に方式を決めない方針は、そのまま維持します。

## 3. 緊急判定の確認文を、通常の調理煙と区別できるものへ

4-5は単語だけの判定から改善していますが、確認文「今、火や煙が出ていますか」に対する「はい」だけで緊急へ移ると、通常の調理煙でも誤判定します。また、「火は出ていない」は、その発言だけで通常と確定できません。

改訂する表現：

> 明白な現在の危険は承認済み案内を直ちに優先する。曖昧な煙の相談は、通常の調理煙・排気不良と、異常な煙・燃焼の可能性を短い確認で区別する。火が出ていないという否定だけで通常と確定せず、他の発言と通話の文脈も評価する。判断不能は安全と断定せず記録する。

評価例に「火は出ていないが、異常な煙が店に充満している」「調理中の煙が排気されない」を追加してください。

## 次に進めること

ユーザーへ依頼する回線情報は、v2の3点を維持します。

1. 092の正確なサービス名
2. 0120の契約上の着信先
3. 主装置のメーカー・型番、契約上の同時通話数

情報が未取得でも、承認済み要件の整理、評価台本、候補音声の公式対応表、模擬データでの検証準備は進められます。実契約・実回線を変更する作業は、成立条件と費用を具体化した後に実施判断します。

なお、3-3の「3/n」は独立性と同じ誤り確率等を仮定した統計的な目安です。手作りのシナリオ試験から、本番の誤り率上限を保証できるという表現にはしません。
