# AI受電コンシェルジュ：設計議論用プロンプト v1

作成日：2026年10月4日

あなたは、日本国内の企業向け電話システムとリアルタイム音声AIを設計する技術責任者です。以下の要件を、もう一人の設計AIと検討しています。目的は、実装AIが曖昧な判断や推測に頼らず開発できる、実装用プロンプトを完成させることです。

今回の依頼は設計レビューと改善提案です。コード実装、外部サービスの契約、電話設定の変更、本番公開は開始しないでください。要件への単純な賛同で終えず、成立しない前提・抜け漏れ・過剰な機能を指摘し、代案を示してください。説明は日本語で、判断理由と根拠を簡潔に示してください。

## 2. 自然な会話の要件

- 一問一答の固定メニューに押し込めず、相手の説明を聞き、不足した情報だけを確認する。
- 先に聞き取れた情報は再質問しない。原則、一度に聞くのは一つの内容にする。
- 言い直し、訂正、話題の途中変更、複数の用件を扱う。
- AIの発話中にお客様が話し始めたら、発話・再生を適切に止めて聞く。短い相づちと、本当の割り込みを区別できるか評価する。
- 割り込み時は生成停止だけでなく、再生待ち音声の破棄と会話履歴の整合を扱う。相手に聞こえていない案内を説明済みにしない。
- 電話番号、日付、時刻、金額は、聞き取りやすい速度と区切りで読み上げる。
- 電話番号・重要な日時は、必要な場面で復唱確認する。「明日」等は日本時間の通話日時を基準に解釈し、曖昧なら確認する。
- ロボット感を抑えた複数の声を試聴・選択できる。希望の例は、ハキハキした女性の声、優しい男性の声。
- 相手が設備名や型番を知らなくても相談を受け付ける。専門用語、名前の漢字、住所の細部を無理に聞き続けない。
- 非通知、無言、雑音、途中切断、聞き取り不能でも、取得できた情報と未確認事項を残す。
- 冒頭にAI受付であることを短く知らせる案を含め、録音する場合の案内と録音を望まない場合の扱いを提案する。

「有人と同等の正確さ」は目標として扱い、未検証の保証にしないでください。通話後の人による補正で、通話中の誤案内まで解消できるとは扱わないでください。

### FAQ回答の境界

- 管理者が公開・承認したFAQを回答根拠にする。Web検索結果やAIの一般知識だけで、会社の提供条件を作らない。
- FAQの言い換えは許容するが、条件・例外・金額の意味を変えない。
- 清掃料金の目安と正式見積もり、希望日時と予約確定を明確に区別する。
- 深夜作業への対応を、深夜の有人電話受付や即日訪問の保証と混同しない。
- 根拠がない質問は確認事項として担当者へ渡す。故障原因や安全性を電話だけで断定しない。
- 緊急性の高い発言を通常の見積受付と同じ扱いにしないための最小限のルールも提案する。

## 4. 電話の切り替えとWeb管理画面

- 普通受電：現在の会社電話機で人が受ける。
- AI受電：AIが会話して受け付ける。
- 時間指定：曜日・時間帯の設定に基づいて上記を切り替える。
- 現在有効なモードをスマホでも一目で確認でき、少ない操作で変更できる。
- 設定変更は原則として次の着信から適用し、進行中の通話を切断・強制移動しない。
- 手動変更とスケジュールの優先順位、手動変更の解除・期限、臨時休業の扱いを提案する。時間帯はAsia/Tokyo。
- 希望する設定、回線側への適用待ち、適用成功、失敗を区別する。画面のスイッチを変えただけで、実回線が切り替わったように表示しない。
- AI停止や外部API障害時の着信先・音声案内・記録を具体化する。「普通受電に戻す」と書く場合、その経路が同じ障害に依存しないか検討する。
- 両番号の着信が実際に切り替わることを検証する。管理画面の動作だけを検収対象にしない。

通常受電モード中の人同士の通話を録音・文字起こしするかは未確定です。初期要件に勝手に追加しないでください。

## 5. 記録・補正・対応管理

- 保存対象は通話ID、開始日時、着信先、回線から得た発信者番号、確認した折り返し先、相手の名前・店舗、用件、希望日時、未確認事項、文字起こし、要約、録音参照、対応状態。
- 回線から得た発信者番号と、相手が希望・確認した折り返し先は別に保存する。非通知や転送で取得できない場合は不明のまま扱う。
- 名前の漢字、電話番号、日時を推測で埋めない。聞き取った内容・本人確認済み・未確認・人が補正済みを区別する。
- AIの自己申告する確信度だけで確認対象を決めず、重要情報の欠落・訂正・矛盾・復唱結果も扱う。
- 通話後にまず要約を通知し、確認が必要な部分を示す案を基本とする。人の確認待ちで全件の通知を止めない。
- 必要な通話だけ、権限を持つ担当者が録音・該当発言を確認して補正する。補正前の記録と変更履歴を残す。
- 修正が既に送った通知に影響する場合の扱いを定義する。古い通知を無言で正しいものとして放置しない。
- 担当者と「未対応・対応中・対応済み」を共有し、同時操作でも担当の二重取得を防ぐ方法を示す。

人による確認機能を作ることと、確認する人員を常時手配することは別です。全件の有人校正や外部オペレーター契約は前提にしないでください。

## 6. LINE通知

- LINE公式アカウントのMessaging APIから、登録済みの社内担当者それぞれの個人LINEへ送る案を基本とする。
- 初回に友だち追加と担当者への紐付けを行う。友だち全員への一斉送信にせず、管理者が認めた通知先だけに送る。
- グループ通知も選択肢として扱う。公式アカウントの参加条件等は最新の公式資料で確認する。
- 通知内容：店舗名・担当者名・折り返し先・用件・希望日時・未確認事項・管理画面の詳細リンク。
- 録音や詳しい記録は、権限を確認する管理画面から閲覧する。公開URLを知るだけで見られる構成にしない。
- 通話の保存と通知処理を分け、通知失敗でも受付記録を失わない。再試行・重複抑止・失敗確認を設計する。
- APIへの送信成功と、相手の受信・既読・対応完了を混同しない。保証できる範囲を明示する。
- LINEの通数上限・料金・ブロック等を考慮する。メールや他チャットへの通知は拡張候補で、初期必須かは未確定。

## 7. 将来の他社提供に備える範囲

- 最初は自社で使える規模に絞る。将来の販売を理由に、契約・請求・販売サイトまで初期実装に加えない。
- 初期対象は一次受付と折り返し管理に絞る。AIから人へのライブ転送、AI自身からの折り返し発信、予約・見積もりの確定、CRM全般は初期実装に含めない案とする。
- FAQは承認済みの回答を編集・公開できる仕組みから始め、複雑な文書検索基盤を必須にしない。
- 会社ごとの電話設定、FAQ、通知先、スタッフ、通話・録音データを分離できる構成にする。
- 分離は画面だけでなくAPI、保存先、検索、バックグラウンド処理、通知先にも適用する。別会社の情報を取得・送信できないことを検証する。
- 電話会社・音声AI・通知の接続部分は、将来変更できる適切な境界を設ける。多数のベンダー対応を最初から実装する必要はない。
- LINE公式アカウントをサービス全体で共有する案と、導入企業ごとに持つ案の違いを短く比較する。初期運用と将来移行への影響で判断する。
- 録音・顧客情報の保存期間、削除、スタッフの権限、操作履歴、秘密情報の管理を設計する。期間や人数は未承認の数値で固定しない。

## 8. あなたに特に議論してほしいこと

### A. 既存電話を維持した切り替え

NTT側の転送機能を使う案と、クラウド電話・PBX等を介する案を必要に応じて比較してください。既存番号・既存電話機を維持する条件、契約変更、費用、発信者番号の取得、両番号への影響、アプリからの制御可否を整理してください。

「転送が可能」から「自作アプリで転送を自由に制御可能」と飛躍しないでください。利用できる公式API等が確認できなければ未確定とし、画面操作の自動化を当然の前提にしないでください。

### B. 日本語の音声方式

音声を直接扱うリアルタイム方式と、音声認識→会話モデル→音声合成をストリーミング接続する方式を比較してください。具体的な構成候補は最大2案に絞り、日本語の会話品質、割り込み、名前・数字、声の選択、速度制御、実電話の音質・遅延、運用費、実装負担で評価してください。

ブランド名だけで採用を決めず、公式に確認できる機能と実測が必要な品質を区別してください。日付・料金・モデル名・国内番号の条件など変わる情報は、最新の一次資料で確認し、URLと確認日を付けてください。

### C. 実用性と費用

月間通話件数・平均通話時間・最大同時通話数・月額予算はまだ不明です。設計全体を止めず、仮定を明示して進めてください。

費用は、番号・転送・着信通話・音声AI・サーバー・録音保存・LINE通知を分けて式を示してください。試算を出すなら、仮の利用量と税・為替・料金確認日を明記してください。一次応対が受電専用でも、構成によって転送区間の通話料が生じ得る点を見落とさないでください。

## 9. 検証と完成判定

実装AIに渡す最終プロンプトには、少なくとも次の検証条件を含めてください。

- 実電話での着信→会話→受付保存→指定したLINE宛先への通知→担当割り当て→対応完了が一通り動く。
- 0120番号と092番号の両方で、普通受電・AI受電・時間指定が設定どおりに動く。
- スマホの管理画面から変更した設定の適用結果を確認でき、通話中の切り替えでもその通話を壊さない。
- 割り込み・相づち・言い直し・長めの説明・雑音・非通知・途中切断のケースを検証する。
- 電話番号・日時は正しく記録されるか、未確認として明示される。誤った値を確認済みにしない。
- FAQにない金額や条件、予約確定を作らない。
- 通知先違い、重複イベント、再送、上限超過、音声AI停止、再起動、想定同時着信数を検証する。
- 別会社・別権限のデータ取得を拒否する。
- 応答時間は「お客様の発話終了から実際に返答音声が聞こえるまで」、割り込みは「相手の発話開始からAI音声が止まるまで」で測り、平均だけでなく遅いケースも報告する。
- 「自然」「速い」「正確」だけで完成判定しない。数値目標・サンプル数・測定条件を提案し、合意値と実測値を分ける。

開発・自動テスト・音声比較・テスト番号での接続検証は実装側が進める案を基本にし、ユーザーへの途中確認や手作業を繰り返し要求しないでください。ただし、実回線への接続を一度も確認せずに本番完成と判定してはいけません。ユーザーしか行えない契約確認や最終試験は、必要最小限にまとめてください。
