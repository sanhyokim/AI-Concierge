# AI受電コンシェルジュ：設計レビューへの返答・改訂依頼 v2

対象：design-review-v1.md／確認日：2026年10月4日

回線調査と音声の比較検証を先行する方針に賛成します。確認済みの事実・提案・未確認事項を分けた整理、電話経路での音声評価、発信者番号と折り返し先の分離、通知の再送設計も維持してください。

ただし、回線案1と音声案Bを確定するには根拠が不足しています。以下を反映した設計レビューv2をお願いします。今回の依頼は設計の改訂です。契約、実回線の設定変更、外部への通知、公開は別途実施判断の対象です。

## 1. 回線に関する断定を、契約ごとの条件付き判断へ修正

ユーザーが確認したのは「0120-77-3408と092-504-2185の両方で同じ会社の電話機が鳴る」ことです。0120の着信先が092であること、092の契約サービス、PBX・主装置の構成は未確認です。

| v1の記述 | v2での扱い |
| --- | --- |
| 0120の着信先に050を指定できない | 一律の禁止としない。NTTの契約条件は対象回線を区分しており、COTOHAの050を契約回線にできる公式案内もある。Twilioの050を直接指定できるかは別の確認事項とする。[1][2] |
| Windowsのみ動作保証だからスマホ不可 | 「サポートされたスマホ操作方法を確認できていない」とする。動作保証外を利用可能とも判断しない。 |
| 公開APIが見つからないので常時転送が唯一 | 「公開APIは未確認」とする。実契約・PBXを確認したうえで、常時転送案の成立条件を評価する。 |
| 人の受電では追加番号・番号非表示が必ず生じる | Twilioから一般電話回線へ再発信する案の制約として示す。既存PBXへのSIP接続等は、対応機器・キャリア条件が成立する場合の比較対象にとどめる。利用可能と決めつけない。 |

「0120からクラウド番号へ直接着信させる経路」と「現在の着信回線で一度受けてから転送する経路」を分けて記述してください。

元の着信番号を取得できなければ「不明（0120または092）」で記録します。同じ会社の共通受付は可能なので、番号識別だけを目的とした追加回線を初期必須にしません。ウィスパー例の「0120経由」も、取得できた場合だけ読み上げます。

ループしない事務所への経路、同時着信数、元の発信者番号、クラウド障害時の復旧手段は、実契約に即して確認します。深夜や外出先でも復旧できるかを含め、単に「NTTへ戻す」で済ませないでください。

## 2. 音声方式は、主要要件をすべて満たしてから選ぶ

ユーザーが重視しているのは、継続的で自然な日本語会話、割り込み対応、重要な内容だけの減速、複数の自然な声の選択です。これらを初期の必須条件として維持してください。

「Bが遅延目標を満たさなければA」ではなく、A/Bを同じ条件で比較し、必須条件を満たした案から品質・費用・運用負担で選びます。先に試作する順番と、最終採用の決定は分けてください。

公式仕様の確認結果：

- ConversationRelayのElevenLabs音声は、voice属性でspeed等を設定できます。「Relay経由では話速設定が未確認」という部分は更新できます。ただし、通話全体の話速設定と、発話中の重要箇所だけの減速は別です。[3]
- 同資料では、ElevenLabsのSSML対応は英語のphonemeに限定されています。日本語でprosodyタグを渡せば部分減速できるとは扱わないでください。必要ならBの中でGoogle等の音声を比較し、採用音声・モデルごとの対応を確認します。[3]
- OpenAI Realtimeにも複数音声と、割り込み時に未再生部分を会話から除く仕組みがあります。声の選択や割り込み履歴の扱いだけでBを優位と確定できません。接続方式による実装差も明記してください。[4]

以下を両案に共通する評価表へ追加してください。

| 必須要件 | 試験と合格判断 |
| --- | --- |
| 継続的な会話 | 用件の追加、途中の質問、言い直し後も文脈を保つ。既に取得した情報を理由なく再質問しない。 |
| 部分的な減速 | 同じ声で「通常の説明→番号・日時をゆっくり→通常速度へ復帰」を実演する。数字のカナ化だけを合格理由にしない。 |
| 複数の声 | 少なくとも希望に沿う明瞭な女性系・穏やかな男性系の候補を用意し、公開する各音声で電話経路の品質を確認する。 |
| 割り込み | 発話を止めるだけでなく、訂正を受けて自然に続ける。「はい、違います」等を相づちとして捨てない。 |
| 聞き取りと復唱 | 数字・日時・店舗名の訂正を保存値まで反映する。確認できない値を推測で確定しない。 |

v1の遅延・停止時間・自然さの数値は「提案目標」のまま維持できます。測定地点も明記してください。クラウド側録音による遅延は発信者端末での体感遅延と同一ではないため、代表条件で端末側の確認も行います。有限の試験で誤確定0件だったことは、本番での誤りゼロ保証と区別します。

## 3. 録音拒否・AI拒否・障害時の仕様を整合させる

次の状態を分けてください。

- 録音の保存可否
- AIへの音声送信・文字起こしの可否
- 受付情報として保存できる項目

録音停止だけではAI処理は停止しません。AI処理を拒否された場合にDTMF受付を提案するなら、AIへの音声送信を切り離し、事前収録音声とプッシュボタンで成立する経路を設計してください。拒否前のデータ、無入力・入力不能時の終了、障害時にも拒否状態を引き継ぐ扱いを定めます。

「普通受電として最初から担当者へ接続する」ことと、「AI会話の途中で担当者へライブ転送する」ことを区別してください。後者は初期対象外です。普通受電の不応答を自動でAIへ回す動作も、未合意の追加機能として扱います。

AI障害時の基本案は、承認済み案内、取得済み情報の保全、受付状況の通知です。録音拒否中に無条件で留守録へ切り替えないでください。

海外処理の判断をユーザーへの一括した「許可できますか」で終わらせず、送信先、処理地域、目的、保存期間、学習利用、削除条件を具体化してください。そのうえで会社としての運用判断と法令上の確認を分けます。録音保存をしなくても外部での音声処理がある構成は、その点を明示します。

## 4. 緊急判定をダクト業務に合わせる

「煙」「におい」「熱い」という単語だけで緊急にしないでください。通常の調理煙・排気不良の相談、過去の出来事、否定表現を区別します。一方で、安全だとAIが断定する運用にも変えません。

明白な現在の危険は承認済みの緊急案内を優先し、折り返し先の聴取で案内を遅らせない設計とします。曖昧な場合の短い確認と「判断不能」の記録も定めてください。

評価には、危険事例に加えて「調理中の煙を吸わない」「昨日焦げ臭かった」「火は出ていない」等を含め、見逃しと誤判定の両方を報告します。緊急案内の既定文も承認対象に含めます。

## 5. LINEの受付状態・再送条件を修正

公式仕様では、再送キー付きリクエストの409は同一リクエストの受付済みを示します。受信者への到達保証ではありません。キーは初回から指定し、有効期間は初回リクエストから24時間です。[5]

改訂する設計：

- 「宛先×通話×通知版」を永続的に識別し、同一通知の再試行では本文・宛先・キーを変えない。
- 200と該当する409の画面表示を「LINE受付済み」に統一する。
- 429を一括して再試行せず、エラー理由を調べ、一時的な制限と月間上限等を区別する。原因不明時の停止・確認条件も定める。
- 24時間を超えた受付結果不明の通知は、新キーで自動送信しない。重複の可能性を表示して扱いを決める。
- 訂正通知は別版とし、元の通知の遅延送信で訂正内容が分かりにくくならないよう順序を管理する。
- 通知障害は管理画面で確認できるようにする。同じLINE経路だけに障害通知を依存させない。メール等は必要性に応じて追加判断する。

通知先は承認された担当者に限定します。個人LINEへの個別通知を優先し、グループ通知も選べるという方針を維持してください。

## 6. 費用・確認事項を、判断できる形へ整える

v1の約76ドルは、仮定した900分の有人通話についてのクラウド側費用差です。追加負担の総額ではありません。同じ前提ならNTT転送費の差は900分×F円/分となり、追加番号・オプション・税等の差も別途整理が必要です。

見積もりでは次を明示してください。

- 1つの共通着信先で済む場合と、2つ必要な場合の番号数・理由。
- 既存費用、追加固定費、AI通話の変動費、有人通話の追加変動費。
- 日本向け料金を確認した項目と、未確認の参考単価。料金表の不一致も未解決のまま明示する。
- 実際の件数・通話時間が未確認なので、例示の200件・300件をユーザー実績として扱わない。

回線確認の依頼は、まず「092の正確なサービス名」「0120の契約着信先」「主装置のメーカー・型番とチャネル数」が分かる部分に絞ってください。契約書全文の提出を必須にせず、不要な顧客番号・支払情報等は伏せられる形にします。

実回線試験は、準備・一時切替・試験・復旧をまとめた作業枠として示してください。1回の操作で済むとは約束しません。評価の大半は実装側で行い、ユーザーには短い受入確認をまとめます。
