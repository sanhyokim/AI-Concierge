## 1. 動かし方

このクラウドの環境から、利用者がURLで開ける安全なプレビューは用意できません（外部からつなげる入口がない）。そのため、**利用者のPCで動かします**。必要なのはPython 3.11以上だけで、追加のパッケージや有料のサービスは要りません。

```bash
git clone https://github.com/sanhyokim/AI-Concierge.git
cd AI-Concierge
git checkout claude/new-session-w4sjel
python3 -m prototype.admin
```

1. コンソールに表示される `http://127.0.0.1:8780` をブラウザーで開きます。
2. ユーザー名 `admin` と、最初の起動のときにコンソールに**1回だけ**表示されるパスワードでログインします。
   - パスワードを自分で決めたいときは、起動の前に環境変数 `ADMIN_PASSWORD` を設定します。
3. 上の「着信テスト」の画面で「着信を入れる」→「例の会話を流す」→「通話を終える」と押すと、一連の動作を確かめられます。

**スマートフォンで試す場合**（同じWi-Fiの中だけ）

- PCで次のように起動し、表示された `http://<PCのIPアドレス>:8780` をスマートフォンで開きます。

  ```bash
  python3 -m prototype.admin --host 0.0.0.0
  ```

- HTTPSではないため、自宅・事務所のWi-Fiの中だけで、架空のデータで使ってください。
- PCのブラウザーの開発者ツールの「スマートフォンの表示」でも確かめられます。

**外部（出先）から使う場合**

- HTTPS、ホスティング（新しい契約）、役割ごとの権限、パスワードの管理の強化が要ります。
- 今回は行っていません。必要になった時点で、費用と一緒に別途示します。

**データと停止**

- データは `prototype/data/reception.sqlite3` に保存されます（gitの対象外）。設定・FAQ・受付・補正・通知の記録が、再起動の後も残ります。
- 初めからやり直すときは、サーバーを止めてこのファイルを消します。
- 停止は Ctrl+C です。

## 2. 構成と選んだ理由

| 部分 | 選んだもの | 理由 |
| --- | --- | --- |
| サーバー | Python標準ライブラリの `http.server`（スレッド） | 既存の試作とブラウザー試験が同じ構成。追加の依存も契約もない |
| 保存 | SQLite（標準ライブラリ） | 再起動しても残る。1ファイルで扱える。通話の記録と通知の送信待ちを、同じトランザクションで書ける |
| 画面 | 素のHTML・CSS・JavaScript（ビルドなし） | PCとスマートフォンの両方で動く。依存の更新がない |
| 認証 | パスワード（PBKDF2）とサーバー側のセッション | 外部公開前の開発用の認証。HttpOnly・SameSite=Strictのクッキー、更新の要求にはCSRFのトークンと同じ出所の確認。連続の失敗は5分止める |

- 外部のサイトのスクリプトは読み込みません。CSPで、同じ出所のスクリプトだけを許可しています。
- 受付の処理（`prototype/reception/`）は、画面から独立しています。架空の着信テスト、ブラウザー会話試験の各社のアダプター、将来の電話経路が、同じ処理を使います。

## 4. 規則（画面・API・試験で同じもの）

**受電モードの判定**（[仕様書](./spec-draft-v1.md) 2-1、`prototype/reception/routing.py`）

1. 手動の「常時AI受電」「常時普通受電」は、スケジュールを見ません。
2. 「スケジュール運用」は、着信の日時（日本時間）で判定します。優先順位は次のとおりです。
   - 特別日（終日）
   - 曜日ごとの時間帯：開始以上・終了未満。9:00〜17:00なら、16:59:59までが対象で、17:00から時間外です。
   - 時間外の扱い
3. 判定がAI受電で、着信の時点でAIが使えないときは、障害時の動作（普通受電、または録音の案内とプッシュボタン）が優先します。
4. 普通受電の判定では、AIの会話を始めず、「普通受電へ渡す」判定だけを記録します（デモでは電話機を鳴らしません）。

**通話の開始時の設定**

- 着信の時点の受電モードの判定・FAQ（有効なもの）・声・保存の規則を、通話に保存します。
- 通話中に管理画面で変えても、その通話は変わりません。次の着信から使います。

**受付項目と確認**

- 「聞き取り」と「本人確認済み」を分けます。番号・日時は、復唱して明確な肯定を得るまで、確認済みにしません。
- 「はい、違います」は肯定として扱いません（サーバーが確認を拒否します）。試験用の規則の応答は、わざとこの場面で確認を求め、サーバーが拒否することを画面で見られるようにしています。
- 要約と通知では、項目ごとに状態を書きます。未確認の値を、確認済みとして書きません。
- 担当者の補正は「担当者が補正」とし、本人確認済みにはしません。補正の前と後・理由・補正した人を残し、要約と通知の新しい版を作ります。

**同意と、AIへ送らない場合**

- 録音の保存、AIへの音声送信、保存してよい項目は、別々に扱います。
- 次の場合は、アダプターが求めても、AIへ内容を送らず、AIの業務処理も受け付けません。
  - 普通受電の通話
  - AIを拒否された通話
  - プッシュボタンの経路
  - 終わった通話
- AIの拒否より前の文字起こしは削除します。
- 「人と話したい」には、折り返しを説明し、短いAI受付を続けてよいかを一度だけ確かめます。
- 保存しない設定の項目は、保存も要約も通知もしません。文字起こしを保存しない設定では、発話の本文を残しません。
- 緊急（明白・判断不能）は、通話の終了を待たずに全宛先へ「緊急／要注意」の通知を作ります（文言は未承認）。

**通知**（[仕様書](./spec-draft-v1.md) 1-8、設計レビュー v2.1 4-6）

- **作り方**
  - 通話の記録と同じトランザクションで、宛先ごとに通知の送信待ちを作ります。
  - 同じ「宛先×通話×版」は1件だけです。通知イベントを再投入しても増えません。
  - 再送キーは最初の送信の前に作り、再試行でも変えません。
- **結果ごとの扱い**

  | 結果 | 扱い |
  | --- | --- |
  | 200、または同じキーで409 | 受付済み（届いた・読まれたとは表示しない） |
  | 500・時間切れ | 同じキーで、間隔を延ばして再試行 |
  | 429（一時的な上限） | 3回で止めて人が確認 |
  | 429（月の上限） | その経路を止め、画面の上部に表示（人が再開） |
  | そのほかの4xx | 止めて人が確認 |
  | 24時間を過ぎても結果不明 | 「重複の可能性あり」。人が再送（【再送】・新しいキー）か破棄を選ぶ |

- **訂正**：版の順に送ります。まだ送っていない古い版は、新しい版に統合します（「訂正済み」）。送った後なら、新しい版の冒頭に「先ほどの通知を訂正します」と入れます。
- **LINE**
  - 公式のMessaging API（push、X-Line-Retry-Key）の要求の組み立てまでです。送信先の登録・接続設定・送信の承認が済むまで、送りません。
  - 個人LINEの非公式な操作は使いません。
- **初期の宛先**（すべて架空）
  - 担当者A：成功
  - 担当者B：1回目だけ500、再試行で成功
  - LINE公式アカウント：未接続・無効

**要約**：固定の規則で作ります。会話モデルの要約ではなく、本番の要約の品質を示すものではありません。

## 5. 確認の結果（2026-10-07）

試験の種類を分けて示します。画面の自動試験の合格は、日本語の会話や電話経路の合格を意味しません。

| 種類 | 内容 | 結果 |
| --- | --- | --- |
| 偽のAPI・業者なしの試験（Python） | 受付の共通処理・判定・通知・管理画面のHTTP・ブラウザー試験のサーバー（業者は偽のHTTP） | 全体122件のうち120件、合格 |
| ブラウザーの自動試験（Chromium） | 管理画面をPC幅（1280px）とスマートフォン幅（390px）で操作する44項目と、ブラウザー会話試験の画面（偽のマイク・オフラインの模擬） | 2件（44項目を含む）、合格 |
| 実際の業者への接続 | — | **未実施**（アカウント・鍵・予算が未承認） |
| 実際の電話 | — | **未実施**（会社回線・試験用の番号とも未接続） |

**完了条件ごとの確認**（指示書 6章）

1. **画面の操作と保存**
   - PC幅とスマートフォン幅で、主要な画面を操作できます（スマートフォン幅で横にはみ出さない）。
   - 受電設定を保存し、サーバーを止めて起動し直した後も残ることを確かめました。設定・受付の記録も、データベースを開き直した後に残ります。
2. **時間帯の境界**：スケジュールの画面の判定で、日本時間の次の時刻を確かめました（単体試験でも同じ）。
   - 8:59:59 はAI受電
   - 9:00:00 は普通受電
   - 16:59:59 は普通受電
   - 17:00:00 はAI受電
   - 土曜はAI受電。土曜の時間帯を追加して保存すると、普通受電
   - UTCで渡した時刻は、日本時間に直して判定
   - 常時モードは、どの時刻でも同じ
3. **通話中の設定変更**：通話中に、別のタブでFAQ-01を無効にし、受電設定を常時普通受電に変えました。
   - その通話は、AI受電のまま、FAQ-01で答えます。
   - 次の着信は普通受電になります。
   - 声の変更も、次の通話からです。
4. **FAQの変更**：スケジュール運用に戻した次の通話では、無効にしたFAQ-01は使われず、「担当者が確認してご連絡します」と答えて、確認事項に記録します。業者へ渡す指示文からも外れます。
5. **訂正した番号**：「090-1234-5678 → はい、違います。…5679」と訂正し、肯定を得た後の値が、次のすべてで一致し、誤った番号が残らないことを確かめました。
   - 受付記録（本人確認済み）
   - 要約
   - 2つの宛先のプレビューと通知本文
6. **宛先ごとの結果と、重複しないこと**
   - 宛先ごとの成功と再試行待ちが記録されます。
   - 再試行は同じ再送キーで行われ、成功します。
   - 同じ通知イベントを再投入しても、0件で増えません。
   - 月の上限・一時的な上限・400・24時間・訂正の版も、単体試験で確かめました。
7. **ログインと鍵**
   - ログインしていないと、設定・受付記録・会話試験のAPIに入れません（401、または画面はログインへ）。
   - 別のサイトからの要求やCSRFのトークンのない更新は、断ります（403）。
   - 偽の長期キーを環境変数に置いて動かし、次のどこにも出ないことを確かめました。
     - APIの応答
     - 画面
     - サーバーのコンソール
     - 操作履歴
8. **AIへ送らない処理**：次を確かめました。
   - **普通受電の通話**：発話をAIへ送らず、業務処理も受け付けません。要約・通知も作りません。
   - **AIを拒否した後**：AIへ送らず、拒否の前の文字起こしを削除します。プッシュボタンの経路へ移り、番号の確認（1）で本人確認済みとして保存します。
   - **保存しない設定の項目**：保存・要約・通知に出ません。
   - **文字起こしを保存しない設定**：発話の本文を残しません。

## 6. まだ作っていないこと・制限

- 手動の固定の期限（次の切替まで、など）。今は、固定中に画面で警告します。
- 役割（管理者と担当者）、担当の割り当てと二重取得の防止、テナントの分離。
- 保存期間による自動削除（期間の設定と警告だけ）。
- 録音（デモには音声がない）。回線の状態の表示（「回線に反映された」）。試験発信による経路の確認。
- 外部公開のためのHTTPS・ホスティング。
- 会話モデルによる要約。試験用の規則の応答は、決まった言い回しだけを扱います。
