## 1. 確定した利用者要件

### 1-1. 目的と範囲【合意】

会社の受電をAIが一次対応し、自然な日本語の会話で用件を整理します。担当者は通知を読み、必要に応じて折り返します。

| 項目 | 内容 |
| --- | --- |
| 展開 | まず自社で利用し、将来は他社にも提供したい |
| 既存番号 | 現在の会社番号を継続する |
| 対象番号 | 0120-77-3408、092-504-2185 |
| 現在の着信 | どちらの番号にかけても同じ会社の電話機が鳴る（経路・契約機能・API連携の可否は確定していない） |
| AI対応の範囲 | 用件・折り返し先を受け付けて担当者へ通知。担当者が折り返す |
| 受電設定 | 普通受電、AI受電、曜日・時間帯による切り替え |
| 管理画面 | 出先からスマホ・PCで操作できるWebアプリ |
| 設定項目 | 受電モード、営業時間、FAQ、音声、通知先 |
| 通話確認 | 要約・文字起こし・録音の確認と、必要な内容の補正 |
| 通知 | 複数担当者それぞれの個人LINE。グループ通知も選択肢 |
| 対応管理 | 担当者と、未対応・対応中・対応済みを共有する |

### 1-2. 完成条件【要件】

1. **切り替え**：PC・スマートフォンのWeb管理画面から、普通受電／AI受電／時間指定を設定でき、設定の保存後、次の着信から意図した動作になる。キャリア側の手動操作を必要とする案は代替運用として示し、同等の要件達成とは扱わない。対応できる経路が成立しない場合は、その不足と代案を示し、要件を変えるかを利用者が判断する。
2. **一連の動作**：実電話での着信 → 会話 → 受付保存 → 指定したLINE宛先への通知 → 担当割り当て → 対応完了が一通り動く。
3. **両番号**：0120と092の両方で、普通受電・AI受電・時間指定が設定どおりに動く。通話中に設定を変えても、その通話を壊さない。
4. **実回線**：実回線への接続を一度も確認せずに、本番の完成とは判定しない。
5. **判定の仕方**：「自然」「速い」「正確」という言葉だけで完成と判定しない。数値目標・サンプル数・測定条件を決め、合意値と実測値を分けて記録する（4-3）。

### 1-3. 会話の必須条件と、採用の決め方【要件】

初期導入の必須条件は次のとおりです。上ほど重要です（利用者の決定、2026-10-05）。

| 重要度 | 必須条件 | 試験と合格の考え方 |
| --- | --- | --- |
| 1 | **AIの発話中も聞き、状況に応じて対応する** | 短い相づちで毎回止まらない。「違います」「訂正します」「ちょっと待って」には速やかに応じる。言い終えていない内容を、伝えたことにしない（共通会話C1〜C3） |
| 2 | **日本語で自然な会話が続く** | 間・語尾・敬語・言い直し・文脈の理解・聞き返し。処理の途中も、追加や訂正を受け付ける。取得済みの情報を理由なく聞き直さない（C4・C5、評価台本のC区分） |
| 3 | 電話番号・日時の明瞭な復唱と確認 | 区切って明瞭に復唱し、明確な肯定を得てから確定する。数字・日時・店舗名の訂正を保存値まで反映し、推測で確定しない（C2・C6、評価台本のR区分） |
| 3 | 複数の声 | 明瞭な女性系と、穏やかな男性系を少なくとも1つずつ用意する。公開する声はすべて電話経路で品質を確かめる |
| 3 | 電話への接続 | 試験用の電話経路で、ブラウザーと同じ条件を満たす。ブラウザーでの合格を、電話での合格に置き換えない |

**部分減速（番号・日時だけを遅く読む）**【要件の変更】
- 初期導入の必須条件から外しました（利用者の決定、2026-10-05）。技術的に面倒なら、初期導入では保留にします。
- 電話番号・日時の明瞭な復唱と確認は維持します（上の表の3つ目）。
- 比べる場合は参考の項目（4-3のQ-07〜Q-09）とし、採用の条件にはしません。これまでの測り方（同じ文章のN版とD版で、発音速度と区切りの間を分けて測る）は、参考として残します。

**採用の決め方**【要件】
- 必要な会話条件を満たした候補の中から、**コストと性能のバランス**で選びます（利用者の決定）。品質・費用・運用負担の順番だけでは決めません。
- 同じ受付業務・同じ台本・同じ計測（端末での音量）で比べます。会話の自然さ・応答時間・受付成功率と、初期費用・月額総費用・保守負担を、同じ表に並べます（[候補の比較枠](./candidate-comparison-v1.md)）。
- 高額でも性能の差が小さい構成、安くても聞き返しや人の補正が多い構成は、その差を示します。
- 配点（例：性能70%・価格30%）や予算の上限は、利用者が決めない限り置きません。
- 安いだけで、必要な会話条件を満たさない候補は採用しません。
- 「試験で0件」を「本番でゼロ」と書きません。少数の試験で誤りが0件でも、合格基準を達成した証拠や、本番の誤り率の保証にはしません。
- 候補と初回の会話試験の構成は、[候補一覧](./candidates-v1.md)にあります（初回：GPT-Live 1、Gemini 3.8 Live、ElevenAgents、Cartesia Managed Agents。比較の基準：GPT-Realtime-2.1）。採用の決定ではありません。

### 1-4. 対象範囲【要件】

| 動作 | 扱い |
| --- | --- |
| 普通受電：着信の時点の設定で、最初から担当者へつなぐ | 初期の対象 |
| AI受電：AIが会話して受け付ける | 初期の対象 |
| AIとの会話の途中で、担当者へライブ転送する | 初期の対象外（AIの障害時も行わない） |
| 普通受電で誰も出ないとき、自動でAIへ回す | 未合意の追加機能。合意するまで実装しない |
| 普通受電中の、人同士の通話の録音・文字起こし | 未確定。初期の要件に加えない |
| AI自身からの折り返し発信、予約・見積もりの確定、CRM全般 | 初期実装に含めない |
| 将来の販売のための契約・請求・販売サイト | 初期実装に含めない |

### 1-5. 同意と拒否【要件】

- 次の3つを、通話ごとに独立して持つ。
  - 録音を保存してよいか
  - AIへ音声を送り、文字起こししてよいか
  - 受付情報として保存できる項目
- 録音を止めても、AIでの処理は止まらない。そのことを案内する。
- AIでの処理を拒否されたら、AIへの音声送信を直ちに切り離し、事前に録音した案内とプッシュボタンだけで受け付ける。無入力・入力できない場合の終わり方を決めておく。
- 拒否の状態は、障害時やフォールバックの経路でも引き継ぐ。録音を拒否されているときに、無条件で留守録へ切り替えない。
- **「人と話したい」と言われた場合**：それだけではAIの拒否として扱わない。折り返しを説明し、短いAI受付を続けてよいかを**一度だけ**確認する。了承されたら最小限の受付（名前・折り返し先・用件の要旨）を続け、断られたらプッシュボタンの経路へ移る（評価台本 X-02／X-02b）。
- 録音を保存しなくても、外部の事業者で音声が処理される構成なら、その点を明示する。

### 1-6. 確認の規則（R-03）【要件】

- 項目を「本人確認済み」（`confirmed_by_caller`）にするのは、復唱した値に対して、お客様が「はい、合っています」のように**明確に肯定した後だけ**です。
- 訂正の後、肯定の前に確定しない。「はい、違います」を肯定として扱わない。
- 名前の漢字、電話番号、日時を推測で埋めない。聞き取った・本人確認済み・未確認・人が補正済みを区別する。
- AIが自分で申告する確信度だけで確認対象を決めない。欠落・訂正・矛盾・復唱の結果も使う。

### 1-7. 緊急判定【要件】

> 明白な現在の危険は承認済み案内を直ちに優先する。曖昧な煙の相談は、通常の調理煙・排気不良と、異常な煙・燃焼の可能性を短い確認で区別する。火が出ていないという否定だけで通常と確定せず、他の発言と通話の文脈も評価する。判断不能は安全と断定せず記録する。

- 「煙」「におい」「熱い」という単語だけで緊急にしない。安全だとAIが断定する運用にもしない。
- 明白な危険では、折り返し先の聴取で緊急案内を遅らせない。
- 緊急案内の既定文は承認の対象にする（4-2のE-01〜E-03）。
- 評価では、見逃しと誤判定の両方を報告する。

### 1-8. LINE通知【要件】

- 通知先は、管理者が承認した担当者だけ。個人LINEへの個別通知を優先し、グループ通知も選べる。
- 「宛先 × 通話 × 通知の版」を永続的に識別する。同じ通知の再試行では、本文・宛先・再送キーを変えない。キーは最初のリクエストから付ける。
- 200と、同じキーで返った409は「LINE受付済み」と表示する。届いたこと・読まれたことは表示しない。
- 429は理由で分ける（一時的な制限と月間上限など）。原因が分からないときは止めて人が確認する。
- 最初のリクエストから24時間を超えて結果が分からない通知は、新しいキーで自動送信しない。重複の可能性を表示し、人が扱いを決める。
- 訂正は別の版として送り、順番を管理する。
- 通知の障害は管理画面で確認できるようにし、同じLINEの経路だけに頼らない（メールなどは必要性を見て追加を判断）。
- 通話の保存と通知の処理を分け、通知に失敗しても受付記録を失わない。
- 録音や詳しい記録は、権限を確かめる管理画面から見る。公開URLを知るだけで見られる構成にしない。

### 1-9. 着信番号が分からないとき【要件】

- 元の着信番号が取れなければ「不明（0120または092）」と記録する。推測で埋めない。
- 番号を識別するためだけの追加回線は、初期には必須にしない。
- 担当者への案内（ウィスパー）で「0120経由」と言うのは、取得できた場合だけ。

### 1-10. 記録・補正・対応管理【要件】

- 保存するもの：通話ID、開始日時、着信先、回線から得た発信者番号、確認した折り返し先、相手の名前・店舗、用件、希望日時、未確認事項、文字起こし、要約、録音の参照、対応状態。
- 回線から得た発信者番号と、相手が確認した折り返し先は、別に保存する。非通知や転送で取れないときは不明のまま扱う。
- 通話の後、まず要約を通知し、確認が必要な部分を示す。人の確認待ちで全件の通知を止めない。
- 補正は、権限のある担当者が必要な通話だけ行う。補正前の記録と変更履歴を残す。補正が送信済みの通知に影響するときは、古い通知を放置しない。
- 担当者と「未対応・対応中・対応済み」を共有し、同時操作でも担当の二重取得を防ぐ。
- 全件を人が校正すること、外部のオペレーターと契約することは前提にしない。

### 1-11. FAQと案内の境界【要件】

- 管理者が公開・承認したFAQだけを回答の根拠にする。Web検索やAIの一般知識で、会社の提供条件を作らない。
- 言い換えはよいが、条件・例外・金額の意味を変えない。
- 料金の目安と正式な見積もり、希望日時と予約の確定を区別する。
- 深夜の作業への対応を、深夜の電話受付や即日の訪問の保証と混同しない。
- 根拠のない質問は、担当者への確認事項にする。故障の原因や安全性を電話だけで断定しない。

### 1-12. 他社への提供に備える分離【要件】

- 会社ごとの電話設定、FAQ、通知先、スタッフ、通話・録音データを分離する。画面だけでなく、API、保存先、検索、バックグラウンドの処理、通知先にも分離を適用する。
- 別の会社のデータを取得・送信できないことを検証する。
- 電話会社・音声AI・通知との接続部分は、将来入れ替えられる境界にする。多数の業者への対応を最初から作る必要はない。
- 録音・顧客情報の保存期間、削除、スタッフの権限、操作履歴、秘密情報の管理を設計する。期間や人数は、承認のない数値で固定しない。

### 1-13. 進め方の制約【要件】

- 新しい有料契約と、本番番号の設定変更は、成立条件と費用を具体化した後に、別途実施を判断する。
- 開発・自動テスト・音声比較・テスト番号での接続は実装側が進める。利用者への途中確認や手作業は、必要最小限にまとめる。
- 事実・提案・未確認を区別して書く。

## 2. 機能仕様（要点）

詳細は参照先にあります。この章では、何をどう作るかの要点だけを書きます。

| 機能 | 要点 | 状態 | 詳細 |
| --- | --- | --- | --- |

**Q-08の測定方法と根拠**（参考の項目。推奨案。未承認）
- 測定方法：同じ声で、同じ文章を通常版（N）と減速版（D）で読ませる。番号・日時の区間の後ろ（post区間）の発音速度を、両方で測る。発音速度は、モーラ数を、150ms以上の間を除いた時間で割ったもの（`prototype/measure/rate.py`）。比はD÷N。
- 下限0.95の根拠：減速の後、通常の速さに戻ったとみなせる範囲。計測ツールの誤差は、合成信号で最大0.63%で、この幅に比べて十分小さい。
- 上限1.10の根拠：減速の後に早口で取り戻すと、聞き取りにくく、不自然になる。下限だけでは、それも合格になってしまう。
- 見直しの方法：同じ文章を2回読ませたN版どうしのばらつき（実測計画のT1。報告の `n_repeat_spread`）を見る。ばらつきがこの幅に近ければ、幅を見直して改めて確認をお願いする。
- 試作のコードでは、1.10を超えたものを `post_too_fast` として、合格にしない。
