# 設計メモ：AI電話受付への業種特化の組み込み（野田テスト版）

Claude Codeへ：このメモは、開発中のAI電話受付アプリに「業種特化」の3要素（緊急度トリアージ／当番転送／DFY設定）を組み込むための設計指示です。既存コードベースの構成・技術スタック・命名規則を先に確認し、それに従ってください。スタックの変更やフレームワークの差し替えはしないこと。不明点は推測で埋めず、末尾の「未決定事項」に挙げたプレースホルダのまま実装し、TODOとして残してください。

---

## 1. 目的と背景

- 対象アプリ：中小事業者向けAI電話受付。最初のテスト導入先は株式会社野田（飲食店向け換気・排気設備の事業者）。
- 汎用AI受付（IVRy等）との差別化は「受付の賢さ」ではなく、業種ごとの業務ルールを設定として作り込む点に置く。
- そのために、会社ごとに変わる部分をすべてエンジン本体から分離し、「会社別設定（テナント設定）」として外出しする。2社目以降は開発ではなく設定作業だけで導入できる構造が、このプロダクトの資産になる。

## 2. 実装する3要素と優先順位

1. **緊急度トリアージ**（最優先）：通話内容をルール表で緊急度に振り分ける。
2. **当番転送**：トリアージ結果に応じて、ライブ転送／即時通知／記録のみ、を切り替える。
3. **DFY設定層**：上記2つを含む会社固有情報を、提供側が事前設定する設定ファイル／設定データとして実装する。顧客側に設定画面は不要（テスト版では特に）。

---

## 3. 設定層（DFY）の設計

### 3.1 原則

- 会社名、業種、聞く項目、トリアージ判定表、当番表、禁止事項、通知先は、コードにハードコードしない。すべてテナント設定から読む。
- AIの応答文（プロンプト）は、テナント設定から生成する。プロンプト内に会社固有の文言を直接書かない。
- テナント設定のフォーマットは、既存コードベースで自然なもの（YAML／JSON／DBレコード等）から選ぶこと。下記は「含めるべき項目」の一覧であり、形式の指定ではない。

### 3.2 テナント設定に含める項目

```
tenant:
  company_name: ""            # 会社名（名乗りに使う）
  industry: ""                # 業種（例：飲食店向け換気・排気設備）
  business_hours: ""          # 営業時間（時間内／時間外で応答を変える場合に使用）
  greeting: ""                # 冒頭の名乗り文

intake_fields:                # 聞く項目（順序つき）。質問文も設定側で持つ
  - 用件種別
  - 店舗エリア・業態
  - 営業への支障度・緊急度（トリアージ用、3.3参照）
  - 現地調査の希望日（希望として聞く。確定はしない）
  - 折り返し先電話番号と連絡可能時間

triage_rules:                 # 3.3の判定表を設定として保持
  ...

on_call_roster:               # 当番表（転送先の順序つきリスト、曜日・時間帯で切替可）
  - TODO: 実番号は未定。プレースホルダで実装する

notification:
  channels: []                # 例：LINE / SMS / メール（利用可能なものから）
  recipients: []              # TODO: 未定

prohibitions:                 # 言ってはいけないこと（4章）
  ...

fallback:
  transfer_timeout_sec: 20    # 1人あたりの転送応答待ち（初期値。設定で変更可に）
  no_answer_action: "即時通知＋録音・文字起こしを送付"
```

---

## 4. 禁止事項（全テナント共通の核＋テナント設定で追加可能）

AIは以下を絶対に言わない／行わない。これらはプロンプトへの明記に加え、応答の事後チェックでも検出できるよう、リストとして分離して保持すること。

- 値段・料金・見積額を口頭で言わない（「担当が確認して折り返しご案内します」に統一）
- 工事日・訪問日・対応時刻を約束しない（希望日は聞くが、確定は折り返し時に人間が行う）
- 保証・責任・原因の断定をしない（「〜が原因です」と言わない）
- 対応エリア外・対象外の仕事を引き受けない（エリア確認は intake で行い、外れた場合は丁寧に断り、記録する）
- 安全系の事案（火災・発煙・ガス臭など）で、AIだけで完結させない（即時に人間へ）

---

## 5. 緊急度トリアージ（野田＝飲食店向け換気・排気設備の判定表）

### 5.1 設計方針

- 判定は原則ルールベース（決定表）で行う。LLMは「発話から項目（スロット）を抽出する」役割に限定し、緊急度の最終判定は決定表に委ねる。理由：判定の再現性と、誤判定の検証可能性を保つため。
- 判定に必要な質問は最大2つに抑える：「今、営業中ですか」「営業に支障が出ていますか」。他の intake 項目と重複させない。
- 安全系キーワード（火災、煙が出ている、ガス臭い、異音と振動、ブレーカーが落ちる等）は、他の条件より優先して最高緊急度にする。

### 5.2 判定表（初期版）

| 緊急度 | 条件の例（野田の場合） | AIのアクション |
|---|---|---|
| S（安全・即時） | 火災・発煙・ガス臭・感電の恐れ／設備停止で営業が止まっている | 即ライブ転送（当番ウォーターフォール）。全員不応答なら即時通知＋録音・文字起こし送付 |
| A（営業支障・大） | 営業中に行う煙のこもり、排気不良、近隣からの臭い苦情が進行中 | ライブ転送。ただし深夜等の時間帯条件はテナント設定で切替可（初期値は転送） |
| B（通常） | 営業時間外の不具合申告（翌営業日で可）、定期清掃・点検の相談、見積相談、新規出店の換気相談 | 転送しない。intake を最後まで聞き、要約を通知。折り返し案内 |
| C（対象外） | 営業電話、間違い電話、無言、対象外エリア・対象外の依頼 | 丁寧に終了。記録のみ（通知はしない、または日次まとめ） |

- 判定に迷う場合は、1つ上の緊急度に倒す（安全側）。
- 判定結果と根拠（どの条件に当たったか）を必ずログに残す（6章）。

### 5.3 会話フロー（状態遷移の骨子）

1. 名乗り（会社名＋AIであることの明示はテナント設定に従う）
2. 用件の聴取 → スロット抽出
3. 安全系キーワードの先行チェック → 該当すれば即 S として転送フローへ
4. トリアージ質問（最大2問）→ 決定表で緊急度を確定
5. 緊急度に応じた分岐：
   - S／A：必要最小限の intake（折り返し番号・店舗名・状況）→ 転送フロー
   - B：intake を全部聞く → 要約通知 → 終了
   - C：丁寧に終了
6. 転送フロー：当番表の順に発信（1人あたり設定秒数）→ 応答があれば接続し、AIは引き継ぎ内容を転送先に耳打ち（要件要約）→ 全員不応答なら fallback（即時通知＋録音・文字起こし）

※ 転送の実装方式（使用中の通話基盤の機能に依存）は既存コードの方式に従うこと。基盤側に転送機能がない場合は、転送部分をインターフェースとして切り、スタブ実装＋TODOで残す。

## 6. ログと計測（テスト評価のために必須）

通話ごとに以下を構造化して保存する。野田テストの評価指標に直結するので、後付けではなく最初から入れること。

- 総着信数、AI対応完了数、取りこぼし件数
- 緊急度別の件数と、判定根拠
- 転送試行回数、接続成功／不応答、有人引き継ぎ率
- 誤振り分けの検出用に、通話全文（文字起こし）と判定結果を紐づけて保存
- 通知の送信時刻と宛先
- 評価チェックポイント（2週間・30日）で集計できる形にしておく（集計クエリ／エクスポート）

---

## 7. テスト観点（シナリオ）

実装後、最低限以下のシナリオで動作を確認すること（想定発話→期待する緊急度とアクション）。

1. 営業中の店から「煙がこもって店内が大変」→ A（または条件によりS）→ ライブ転送
2. 「排気ファンが止まった。明日も営業がある」→ A → 転送、深夜なら通知への切替が設定通りか
3. 「火が出た／焦げ臭くて煙が出ている」→ S → intake を省略して即転送
4. 近隣住民から「臭いがひどい」と苦情 → A（進行中）として扱い通知／転送
5. 新規出店の換気相談 → B → intake 完走、要約通知
6. 定期清掃の相談 → B → 同上
7. 客が値段を聞く → 禁止事項どおり「担当が折り返し案内」で逃がし、金額を言わない
8. 客が「明日来て」と日程確定を求める → 希望としては聞くが約束しない
9. 営業電話（広告・通信回線の勧誘）→ C → 丁寧に終了、通知なし
10. 転送先が全員出ない → fallback：即時通知＋録音・文字起こしが送られる
11. 対象外エリアからの依頼 → エリア外として記録し、引き受けない
12. 無言・すぐ切れる → C、記録のみ

---

## 8. 実装の順序（提案）

1. テナント設定の読み込みと、プロンプト生成の設定化（ハードコード排除）
2. スロット抽出＋決定表によるトリアージ判定（転送はまだ繋がず、判定とログまで）
3. 通知（要約送付）の実装
4. 転送フロー（ウォーターフォール＋fallback）
5. 計測の集計（6章）
6. 7章のシナリオで検証し、誤判定パターンを一覧化して報告

各ステップ完了時に、変更点と確認結果を簡潔に報告すること。一括で全部作ってから報告、にしない。
